Shipwright guide

Shipwright is a Claude Code plugin named sw. You give it a task with /sw:ship. It researches, interviews you on the architecture, writes a test-first plan, and after you approve the plan it builds, verifies, reviews, documents and opens PRs without further check-ins. Once your change is deployed, it checks it on dev.

Install

Requirements: Claude Code, Node ≥ 20, git, gh (logged in). For database isolation you also need psql/pg_dump and redis-cli. Frontend checks use Playwright.

Option A: plugin only (one step)

claude plugin install sw --marketplace jamesngdev/shipwright

Restart Claude Code. At the first session start, the plugin copies its scripts to ~/.claude/shipwright/bin. /sw:setup can then add the statusline and the CLAUDE.md block.

Option B: full install from a clone

git clone https://github.com/jamesngdev/shipwright && cd shipwright
./install.sh                 # interactive
./install.sh --yes           # accept everything
./install.sh --no-statusline --keep-claude-md-sections

The installer does four things:

  1. Copies the scripts to ~/.claude/shipwright/bin and writes a default config.
  2. Backs up ~/.claude/CLAUDE.md and adds a managed block between <!-- shipwright:start --> and <!-- shipwright:end -->. If you agree, it also moves out the sections Shipwright replaces (Post-Feature Auto-Chain, Feature Branch Hygiene, Branch & PR Base). Uninstall puts them back.
  3. Sets the Shipwright statusline and keeps your previous one for uninstall.
  4. Adds the marketplace and installs sw@shipwright.
If superpowers or another workflow plugin is enabled, the installer warns you. Both would auto-trigger their own flows and compete with Shipwright.

Machine setup: /sw:setup

Run this once per machine. It asks for, or confirms:

  • Local Postgres: used when a repo's DATABASE_URL has no password. Default localhost:5432, user postgres.
  • Local Redis: default localhost:6379.
  • Logs MCP: which MCP server /sw:verify-dev uses to read dev logs. "None" means it only reports failures.
  • Default base branch: master.

It then checks that your tools are installed and offers to install the statusline and the CLAUDE.md block. The settings are stored in ~/.claude/shipwright/config.json.

Repo init: /sw:init

Run this once per repo. Shipwright suggests it at session start if the repo has no CLAUDE.local.md. It detects the following:

  • the stack and package manager;
  • the lint, typecheck, test, coverage, build, dev, migrate and seed commands;
  • the health endpoint and API versioning;
  • where auth guards live;
  • whether the repo has an llms.txt.

Then it asks you for the dev and prod domains and dev test auth, and writes a git-ignored CLAUDE.local.md:

# Local project context (Shipwright) — not committed
## Environments
- Dev: https://api.dev.example.com   · health: /health
- Prod: https://api.example.com      · (read-only — never test against prod)
## Dev smoke-test auth
POST /v1/auth/login {"email":"qa@example.com","password":"…"} → .accessToken
## Commands
- lint: pnpm lint · typecheck: pnpm tsc --noEmit · unit: pnpm test · integration: pnpm test:e2e
- coverage: pnpm test --coverage --coverageReporters=lcov · build: pnpm build · dev: pnpm start:dev

The main command: /sw:ship

/sw:ship "add partial refunds to orders"
/sw:ship "fix: duplicate webhook creates two payments" --small
/sw:ship --resume            # continue the active task in this worktree

Each stage is its own skill, so you can also run any stage on its own, for example /sw:verify before you open a hand-made PR.

Sizes, gates and when it stops

SizeWhenWhat runs
tiny≤ ~20 lines, one file, no schema/API changebranch in place → edit → quick verify → llms-txt → PR
smallone module, no new data model, ≤ ~5 taskscode scout → light architect → plan → worktree → inline build → verify → review → llms-txt → PR → verify-dev
largenew model or migration, contract change, cross-module, concurrency/cache/security impacteverything, including parallel research, plan red-team and subagent build

There are two gates (⛔): the design and the plan. After you approve the plan, Shipwright stops only for:

  1. irreversible or destructive operations;
  2. security-sensitive actions;
  3. side effects outside the worktree that are yours to take (merge, push to shared branches, deploy, publish);
  4. a plan so broken that every way forward is a guess;
  5. verification still failing after 3 rounds (or verify-dev after 2).

Every other decision is made on the spot and logged in plan.md:

## Rulings
- Ruling: store refund reason as enum, not free text — design lists 4 reasons — cost if wrong: one migration

Discover

Discover maps the code first. It uses CodeGraph when the repo has .codegraph/, and targeted Grep/Read otherwise. For large tasks it also runs 2–3 sw-researcher agents (Haiku) in parallel, each with one question:

  • library docs through context7, pinned to your lockfile version;
  • current practices from recent official sources;
  • prior art via gh search code.

The output is a one-page research.md covering current behavior, touch points, constraints, options seen, and risks for the architect.

Architect

The architect stage runs in the main thread. It starts by echoing back what it understood, then asks one question at a time. Each question comes with a recommended option and states what your answer changes. It covers only the items your task touches:

AreaExample
Data model & migrationnew table or column? backfill? migration order vs deploy?
API contractversioning, backward compatibility, pagination, error codes
Consistency · idempotency · concurrencytransaction boundary, double submit, race on the same row
Cache · authz · failure modeskey/TTL/invalidation, ownership checks, timeouts and fallbacks
Performance · observability · rolloutN+1/index/payload, logs and metrics, feature flag and rollback
Frontendloading/empty/error states, optimistic updates, a11y, responsive targets

For large tasks, or anything touching auth, payments, uploads, secrets, webhooks or multi-tenant data, it also runs /sw:threat-model. That pass lists assets, trust boundaries and abuse cases, and gives each threat a mitigation and a test. The result becomes a ## Threat model section in design.md, and the plan turns each mitigation into a test-first task. You can also run it on its own.

Next it lays out 2–3 approaches with their trade-offs and writes design.md, which doubles as the ADR. It does not plan until you approve.

Plan

The plan starts with a file map. Each task then lists exact files, interfaces, a TDD tier, named tests and a "done when" command. Large plans are red-teamed by three personas before you see them: the Breaker (races, partial failure), the Operator (migrations, rollback) and the Skeptic (what to cut). Drafts live in .sw/specs/, which is git-excluded, and move into docs/specs/<date>-<slug>/ in the worktree so they ship with the PR.

Worktree

node ~/.claude/shipwright/bin/wt.cjs create partial-refunds --prefix feat --size large
WhatHow
Location.worktree/feat-partial-refunds, with .worktree/ added to .gitignore
Baseroot worktree's branch, else master/main; never develop
Dependenciesnode_modules APFS-cloned (cp -c: instant, copy-on-write, isolated), with reflink copy and then symlink as fallbacks
Envonly .env, .env.local, .env.development*, .env.test*; never production or staging
Database<db>_wt_partial_refunds on the same server as your DATABASE_URL: a full pg_dump | psql copy up to 100 MB, otherwise schema plus migration history followed by your seed

State.sw-state.json (stage, size, DB, port), which drives the statusline and --resume
The main checkout is never touched. Its .env, DB and Prisma client stay exactly as they were.

Build & tiered TDD

TierForRule
test-firstdomain/service logic, every bug fixwrite the test → watch it fail for the expected reason → minimal code → green
integrationendpoints, handlersreal request → worktree DB → response, success + every documented error
noneconfig, DTOs, wiring, migrationsno test-first, but covered by integration tests

Small tasks are built inline. For large tasks, each plan task goes to a fresh sw-implementer (Sonnet) with a brief file, followed by an sw-spec-checker that compares the diff with the brief (missing, extra or untested). Each task gets a checkpoint commit, and these are squashed before the PR.

Verify

#StepPass
1–2lint, typecheck0 errors
3–4unit, integration0 failures, and no tests skipped by this branch
5coveragecoverage-changed.cjs: every changed source file at ≥ 80% lines
6–7build, dev serverexit 0; health endpoint 200 on the worktree port
8API smokeevery changed endpoint, happy path plus each error case
9Playwright(frontend) flows pass, 0 console errors, 0 failed requests

If a step fails, Shipwright finds the root cause, fixes it and re-runs from that step, for up to 3 rounds. It never weakens tests or lowers thresholds to get a pass.

Temporary auth bypass, done safely

node ~/.claude/shipwright/bin/auth-bypass.cjs start src/auth/jwt.guard.ts   # snapshot first
#   edit: canActivate() { return true; } // @sw-auth-bypass
node ~/.claude/shipwright/bin/auth-bypass.cjs restore                      # always; fails if a marker is left

A hook blocks git commit, git push and gh pr create while any @sw-auth-bypass marker exists. Authorization cases (401/403) are covered by integration tests locally and by real-auth checks on dev.

Review

One sw-reviewer (Opus) reviews the whole branch against design.md and plan.md, using the security and performance lenses and the stack pack references that are relevant. Critical and Important findings are fixed before the PR. Minor ones become follow-ups in the PR body.

llms.txt

This step runs for every feature. For each client-facing change it documents the following, in an llmstxt.org-compliant llms.txt and topic files (default docs/llm/):

  • the endpoint's purpose and auth;
  • request and response, with an example;
  • errors, with codes and what the client should do;
  • relations to other APIs and side effects.

For internal-only changes it records an explicit no-op. /sw:llms-txt audit reports drift as MISSING, WRONG, DEAD or broken links, with diff patches.

Pull requests

  • Squashes to 1–3 commits, but only before the first push. It never force-pushes.
  • Switches the SSH identity you configured per repo owner, for example aw/ap aliases.
  • PR #1 → base branch (kept open, never auto-merged) and PR #2 → develop.
  • If develop conflicts, it creates integration/<branch> from develop, merges the feature into it and opens the PR from there. It never merges develop into the feature branch.
  • The PR body covers the summary, API changes, the verify table, smoke results with re-runnable curl lines, and the rulings. Steps that didn't run are written as "not run — reason".

Verify on dev

Shipwright never merges. It checks the develop PR with gh pr view. After the merge, it asks you to confirm the deploy is live, then:

  • checks the health endpoint and the commit, if exposed;
  • re-runs the smoke table on the dev domain with real auth from CLAUDE.local.md, adding 401/403 cases.

On failure it reads logs through your configured logs MCP. A feature bug gets a test-first fix that is pushed and re-verified, for up to 2 rounds. An infra or config issue is reported with evidence, and Shipwright never changes the environment itself.

Cleanup

/sw:cleanup partial-refunds

Once the base-branch PR is merged, cleanup drops the worktree DB, flushes its Redis db, removes the worktree and deletes the merged branch. It refuses if there are uncommitted or untracked files, unless you confirm with --force.

Debugging: /sw:debug

Debugging works the same way whether you start it yourself or a verify step does: reproduce → trace backward to where the bad state is created → test one hypothesis at a time → write a failing test → fix → add a guard. After three failed hypotheses it steps back, or hands the evidence to sw-debugger for a fresh look. It has specific playbooks for type errors, CI-only failures, dev logs and performance (measure before and after).

FAQ & troubleshooting

"pg_restore: unrecognized configuration parameter transaction_timeout"

This happens when your local pg_dump is newer than the server. Shipwright already uses pg_dump | psql and filters that setting out. If you still see it, update Shipwright.

The DB clone failed with a password error

Add the password to the repo's DATABASE_URL, or set it in /sw:setup. It is used only when the URL has no password.

Not on macOS / APFS

Shipwright falls back to cp --reflink=auto, and then to a symlink. With a symlink, run a real install in the worktree before changing dependencies or the Prisma schema.

A commit is blocked: "Auth bypass still present"

Run node ~/.claude/shipwright/bin/auth-bypass.cjs restore. If it reports markers that were never snapshotted, remove them by hand.

Can I skip a stage?

Yes. Force a size (--tiny), or run individual stages yourself. Shipwright will still never report something as passing without running it.

Uninstall

./uninstall.sh               # or: claude plugin uninstall sw@shipwright

The uninstaller removes the plugin and the CLAUDE.md block, restores the moved sections and your previous statusline, and keeps config.json. Backups are in ~/.claude/backups/.
